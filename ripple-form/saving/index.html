Saving and loading

Every field remembers a baseline: the value it had when the form was built. Comparing with it gives a dirty flag; writing it back is a reset; moving it is a save. Each piece below adds one button to the same profile form.

Knowing when there is something to save

Form.isDirty form () is true while any field differs from its baseline. It is a tracked read, so a button whose disabled reads it follows the fields. The submit button is drawn by hand here, with View.Action.Custom, to give it that attribute.

Save is disabled. Change the name: it lights up. Type Ada back: it goes off again, because the value equals the baseline.

Going back

Form.reset form writes every baseline back. Errors that were showing stay shown until the error visibility is reset too, so the two calls go together.

Clear the name and leave the field: the error shows and Reset lights up. Press it: Ada is back and the error is gone.

Saving

Saving is not the library's business; what it needs to know is that the current values are now the baseline. Form.commit form does that. Call it once the save succeeded, and the form is clean again with the new values.

Change the name and press Save: the line under the form goes back to "Everything saved" and the button goes off, with the new name in the field.

Loading a record

To fill the form from a record, say a profile fetched from the server, describe once how the record maps to the Vars. FormValues is that pair of functions. Form.load values form record then writes every field in one batch and commits, so the loaded record is the new baseline.

Press Load Grace: both fields fill and the form is clean. Edit a field: unsaved. Form.snapshot values is the other direction, the record as it is typed, for a draft or a preview.

Writing a Var from outside

The form owns nothing. Any code can write a field's Var; the field, its parser, every check that reads it and the dirty flag follow. Form.load is exactly that, for every field at once, followed by a commit.
